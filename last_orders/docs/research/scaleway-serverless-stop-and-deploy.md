# Scaleway Serverless Containers: stop, verify and deploy

Research date: 11 November 2026. Scope: official Scaleway documentation, API schemas and first-party client source, plus the user's reported console observation; no infrastructure, credentials or authenticated APIs were accessed.

## Conclusion

**A provably safe stop-then-replace procedure is not established by the sources reviewed.** The API can update configuration and redeploy, and Cockpit reports instance counts, but the reviewed sources do not establish an authoritative termination barrier or a way to prevent every new instance until the operator explicitly starts the new image. Do not equate an idle period, `ready` status or a zero dashboard sample with such a guarantee. This is a documentation gap, not proof that no other mechanism exists.

The user reports that setting both minimum and maximum instances to `0` in the Scaleway console works and shows a **shutting down** status. This is a useful observation of that console interaction, not independent proof of API acceptance, completed termination, or a no-restart guarantee. The precise console request, underlying status and subsequent behaviour were not observed in this research.

Confidence is **high** for the documented behaviours below; **limited** for operational guarantees that the documentation does not specify. Direct API acceptance and the effect of `max_scale=0` remain unverified.

## Scaling and traffic

- With request-concurrency autoscaling, `min_scale=0` permits scale-to-zero after 15 minutes of inactivity; it does not immediately stop the container or prevent later scale-up. CPU- and RAM-based policies require a minimum of 1. The documented 15 minutes is an inactivity rule, not a confirmed termination barrier for active or in-flight work. [Autoscaling reference](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-autoscaling/)
- `max_scale` is the maximum instance count. Both v1 and deprecated v1beta1 update schemas represent the two scales as optional nullable `uint32` fields, but do not specify the server-side minimum, the `min_scale`/`max_scale` relationship, or whether an explicit zero maximum is accepted, defaulted, rejected or enforced as a stop. The user's console observation is evidence for that interaction, not a direct API test. The published maximum is 200 instances, subject to quotas. [v1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1/schema.yml), [v1beta1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1beta1/schema.yml), [limits](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-limitations/)
- HTTP gateway requests and configured CRON, SQS or NATS triggers can invoke the container. Incoming traffic can keep it active or cause a cold start; the reference says requests are queued at maximum scale and can receive 503 when the queue is full. This describes ordinary maximum-scale behaviour, not a guarantee about `max_scale=0`. [API overview](https://www.scaleway.com/en/developers/api/serverless-containers/), [autoscaling reference](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-autoscaling/)
- Scaleway says its own health checks do **not** wake a container when no instance is up. A separate external request to the public or private `/healthz` endpoint is instead an HTTP invocation and can wake it; do not use that request as a passive stop check. The v1 schema describes liveness checks during an instance's lifetime and startup checks during startup. [FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#how-do-serverless-containers-health-checks-work), [v1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1/schema.yml), [API overview](https://www.scaleway.com/en/developers/api/serverless-containers/)
- Disabling the default public endpoint makes that endpoint return 404, but custom domains can still exist and private endpoints and triggers are separate invocation paths. It is not documented as a global pause or termination barrier. [Container API](https://www.scaleway.com/en/developers/api/serverless-containers/containers), [triggers API](https://www.scaleway.com/en/developers/api/serverless-containers/triggers)

## Candidate API and client mapping

For an existing container, the schema-supported candidate corresponding to the two settings is `PATCH /containers/v1/regions/{region}/containers/{container_id}` with `Content-Type: application/json` and the following body:

```json
{"min_scale": 0, "max_scale": 0}
```

The deprecated v1beta1 equivalent is `PATCH /containers/v1beta1/regions/{region}/containers/{container_id}` with the same scale field names and JSON body. These are **candidates inferred from the schemas**, not a captured console request or an independently tested stop command. Both schemas permit these JSON integer fields syntactically; neither establishes that the service accepts their combination or what it does. The v1 schema explicitly says omitted fields remain untouched on update: `{}` and `{"min_scale": 0}` are not equivalent to the two-zero body. `null`, omission and zero are distinct JSON representations; the schemas allow null but do not establish its update semantics, so do not substitute it for zero. Create-time defaults are a different question from partial updates, and the reviewed schemas do not specify default scale values. [v1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1/schema.yml), [v1beta1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1beta1/schema.yml)

- **Go SDK:** Both versions' `UpdateContainerRequest` use `*uint32` with `omitempty` for `MinScale` and `MaxScale`; a non-nil pointer to zero retains the numeric field, while nil omits it. The generated `UpdateContainer` sends a PATCH. This establishes client representation, not server behaviour; other SDK fields may also be serialised, so the example above is the minimal direct HTTP body, not a claim about the SDK's entire payload. [v1 SDK](https://github.com/scaleway/scaleway-sdk-go/blob/main/api/container/v1/container_sdk.go), [v1beta1 SDK](https://github.com/scaleway/scaleway-sdk-go/blob/main/api/container/v1beta1/container_sdk.go)
- **CLI:** The current generated v1 `container container update` command exposes optional `min-scale` and `max-scale` and uses the v1 SDK update request. The v1beta1 generated CLI source currently exposes token commands, not a separate container update command. The source establishes argument availability, not a tested CLI invocation, wire payload or service acceptance; verify the installed CLI version and explicit-zero handling before use. [v1 CLI](https://github.com/scaleway/scaleway-cli/blob/main/internal/namespaces/container/v1/container_cli.go), [v1beta1 CLI](https://github.com/scaleway/scaleway-cli/blob/main/internal/namespaces/container/v1beta1/container_cli.go)
- **Terraform:** The current provider's `scaleway_container` schema makes `min_scale` and `max_scale` optional and computed, with no explicit provider default. On update, each changed field is converted to a non-nil `uint32` pointer, including zero; unchanged fields are omitted. On create, `GetOk` guards both fields, and HashiCorp documents that `GetOk` tests for a non-zero value, so an explicit zero can be omitted from the create request. Do not infer the resulting server default or assume creation and update are equivalent. Terraform plan/state behaviour and the installed provider version still need checking; the source is the moving `main` branch. [Provider schema and update](https://github.com/scaleway/terraform-provider-scaleway/blob/main/internal/services/container/container.go), [request construction](https://github.com/scaleway/terraform-provider-scaleway/blob/main/internal/services/container/helpers_container.go), [GetOk](https://pkg.go.dev/github.com/hashicorp/terraform-plugin-sdk/v2/helper/schema#ResourceData.GetOk)

## Updates, image identity and failure

- The v1 `PATCH` updates only supplied fields, including `min_scale`, `max_scale` and `image`; v1 container updates automatically deploy. Scaleway says updates always redeploy, and deployment uses a rolling replacement in which old instances can continue while new ones start. The FAQ states that every deployment starts a new instance even with `min_scale=0` and no traffic. Thus changing a scale setting itself cannot be assumed to be a passive stop or to establish non-overlap. [v1 migration guide](https://www.scaleway.com/en/docs/serverless-containers/reference-content/v1-migration-guide/), [autoscaling reference](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-autoscaling/), [FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#why-does-my-container-have-an-instance-running-after-deployment-even-with-min-scale-0)
- A mutable tag push alone does not update the deployed image: scaling, including from zero, uses the current deployment's digest. `POST .../redeploy` rolls out the latest image for a mutable reference. A changed image reference can be supplied by `PATCH`, which deploys automatically; do not blindly issue another deployment immediately afterwards, since the migration guide warns this can encounter a transient-state 409. Scaleway recommends immutable versioned tags. [FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#what-are-the-conditions-to-use-an-updated-image), [container API](https://www.scaleway.com/en/developers/api/serverless-containers/containers), [migration guide](https://www.scaleway.com/en/docs/serverless-containers/reference-content/v1-migration-guide/)
- The Registry tag API returns the registry tag's `digest`; the v1 container response documents an image reference, not a separate resolved running/deployed digest. Consequently, a registry digest or configured tag alone does not establish which digest each currently running instance uses. The sources reviewed do not establish whether an `image@sha256:...` reference is accepted or how to attest the active digest. [Registry tags API](https://www.scaleway.com/en/developers/api/registry/tags), [v1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1/schema.yml)
- Scaleway says there is no versioning or automatic rollback. After a failed deployment, the previously deployed version may continue serving requests for up to 24 hours; the documented fallback is temporary, not a rollback guarantee or proof that the old process has stopped. [Limits: versioning and rollback](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-limitations/#versioning-and-rollback)

## Observation and API paths

Paths below are relative to `https://api.scaleway.com` unless stated otherwise. They describe capabilities, not an approved production procedure.

| Operation | Path and evidence |
| --- | --- |
| Inspect or update container | `GET` / `PATCH /containers/v1/regions/{region}/containers/{container_id}`. `status` and `error_message` describe the container resource; `ready` means operational, not zero instances. The response has configured scales, not a live instance inventory. [Container API](https://www.scaleway.com/en/developers/api/serverless-containers/containers), [status definition](https://www.scaleway.com/en/docs/serverless-containers/concepts/#status) |
| Force image refresh | `POST /containers/v1/regions/{region}/containers/{container_id}/redeploy`, body `{}`. This rolls out new instances and terminates old ones; it is not documented as stop-first. [Container API](https://www.scaleway.com/en/developers/api/serverless-containers/containers#redeploy-a-container) |
| Inspect event triggers | `GET /containers/v1/regions/{region}/triggers?container_id={container_id}`. [Triggers API](https://www.scaleway.com/en/developers/api/serverless-containers/triggers) |
| Inspect image tags | `GET /registry/v1/regions/{region}/images/{image_id}/tags` or `GET /registry/v1/regions/{region}/tags/{tag_id}` returns tag digests for Scaleway Registry. [Registry tags API](https://www.scaleway.com/en/developers/api/registry/tags) |
| Discover metrics source | `GET /cockpit/v1/regions/{region}/data-sources?project_id={project_id}` returns source URLs; Cockpit exposes a Prometheus-like metrics query API. [Data sources API](https://www.scaleway.com/en/developers/api/cockpit/regional/data-sources), [Cockpit API](https://www.scaleway.com/en/developers/api/cockpit/regional-api/) |

Cockpit's Serverless dashboard lists **number of instances**, container status and per-instance CPU and memory. Individual instance names appear in their hostname and the `resource_instance` label on logs and metrics. These are useful observations, but the reviewed documentation does not identify a definitive count query, freshness bound, treatment of missing series or terminating instances, or an atomic relationship between a zero sample and future scale-up. Logs and resource-level status are not a complete, authoritative inventory. [Monitoring guide](https://www.scaleway.com/en/docs/serverless-containers/how-to/monitor-container/), [instance concept](https://www.scaleway.com/en/docs/serverless-containers/concepts/#container-instance), [Cockpit supported endpoints](https://www.scaleway.com/en/docs/cockpit/reference-content/cockpit-supported-endpoints/)

The v1 container resource status enum is `unknown_status`, `updating`, `deleting`, `locking`, `ready`, `error`, `locked`, `creating`, `upgrading`; v1beta1 uses `unknown`, `ready`, `deleting`, `error`, `locked`, `creating`, `pending`, `created`, `locking`, `upgrading`. Neither includes `shutting_down` or `stopped`. The user's console label must not be assumed to map to one of these values, or to be an API instance status. Neither reviewed container schema exposes a live instance count or instance-status list, and their published paths contain no container-instance inventory or stop endpoint. `ListContainers.total_count` counts container resources, not replicas. The console's Logging and Metrics tabs provide access to Cockpit observations, not a documented termination barrier. [v1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1/schema.yml), [v1beta1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1beta1/schema.yml), [monitoring guide](https://www.scaleway.com/en/docs/serverless-containers/how-to/monitor-container/)

## Remaining verification for automation

No additional infrastructure is needed to specify the following checks, but they would change or invoke the existing container and require a separately authorised maintenance window; none were performed here. Do not expose tokens or secret environment values in captures.

1. Record the current region, scaling policy, image and both scale settings for restoration. During a deliberate console 0/0 change, inspect a redacted browser network capture: API version, method, path, exact JSON including whether both zeros are present, response code/body, and resource `GET` values before and after. Compare the console label and its timing with API status; do not assume they are the same signal.
2. With explicit authorisation and an agreed recovery plan, compare the candidate direct PATCH and, if relevant, the chosen CLI/provider version against the console interaction. Check acceptance, returned and later configured values, any update-created instance, time to termination, and whether the console status settles. Check in-flight requests and behaviour of HTTP and configured triggers while 0/0 is in force, including queued work and restart attempts. Use logs, metrics and process-specific evidence as observations, not proofs of a complete inventory.
3. Determine whether changing image while 0/0 starts a process, how restoration of the saved scales starts the new deployment, and what happens on failed deployment or retry. Check for overlap between old and new processes and capture version/instance identity where available. Request a supported termination and no-restart barrier from Scaleway before claiming no-overlap; a successful experiment alone cannot establish a universal guarantee.

Any automation would need to preserve the original scale values, transmit explicit zeros rather than defaults, handle asynchronous updates and errors, verify the selected client's actual payload, and restore the intended settings deliberately. An authoritative stop barrier and an image-change/start sequence remain prerequisites for a guaranteed stop-then-replace workflow.

## Question for Scaleway support

For a Serverless Container that must never have old and new processes running concurrently, what **supported API sequence and observable, authoritative barrier** guarantees that all old instances, including terminating and failed-deployment fallback instances, have exited and cannot restart before a new image starts? Please specify:

1. Whether `min_scale=0,max_scale=0` is valid for each autoscaling policy, its validation and exact effect on running, in-flight, queued and future requests, and whether a scale update itself creates a rollout or instance.
2. How to fence public, custom-domain, private, scheduled and queue invocations, including in-flight events; which signal proves termination, its freshness/consistency and whether it covers all replicas and fallback revisions.
3. Whether an image can be changed while fenced without starting it; the precise activation/start call, digest-pinning and running-digest verification, and failure/rollback behaviour. If no such sequence exists, what supported alternative provides the same no-overlap guarantee?

## Verification

Compared the v1 and deprecated v1beta1 OpenAPI schemas with Scaleway's autoscaling, FAQ, monitoring, migration and rollback documentation, and inspected the linked Go SDK, CLI and Terraform provider sources. The v1beta1 schema also says updates always redeploy and documents the older `/deploy` endpoint as superfluous immediately after an update. The console report is user-observed; no live API calls or credentials were used. [v1beta1 schema](https://www.scaleway.com/en/developers/api/serverless-containers/v1beta1/schema.yml)
