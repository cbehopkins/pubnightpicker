# CDD: Event Recurrence and Poll Materialisation

## 1. Purpose

Define the backend architecture and behaviour for recurring event venues.

The service has two responsibilities:

1. Maintain the next occurrence date for recurring event venues.
2. Materialise a poll when an event occurrence enters its poll-creation window.

The design is listener-driven rather than time-based housekeeping.

The system must be safe to replay and retry. Correctness is based on:

- idempotent listener/fact/cell processing;
- deterministic recurrence calculation;
- durable database state;
- explicit business-level existence checks;
- safe re-execution rather than exactly-once assumptions.

---

# 2. Scope

## In scope

- Detection of stale/missing event occurrence dates.
- Calculation of the next recurrence occurrence.
- Updating the venue's stored occurrence date.
- Detection of event occurrences entering the poll-creation window.
- Creation of event polls.
- Creation of associated vote and attendance documents.
- Poll creation audit.
- Idempotency and replay behaviour.
- Recurrence calculation for supported recurrence forms.

## Out of scope

- Poll auto-completion.
- Poll winner selection.
- Notification delivery.
- Application-data deletion.
- Event creation UX.
- Authentication.
- General-purpose housekeeping scheduling.

# 3. Core Architectural Principle

Event recurrence is not implemented as a scheduled housekeeping task.

Firestore state is the source of truth.

Listeners observe venue documents and create Facts when the venue's current state requires work.

Facts create Cells.

Cells perform the actual state-changing work.

Conceptually:

```text
Firestore pubs/{eventId}
        │
        ├── stale/missing date
        │
        ▼
stale_events Listener
        │
        ▼
      Fact
        │
        ▼
   Stale Event Cell
        │
        ▼
calculate next occurrence
        │
        ▼
update pubs/{eventId}.next_occurrence_date

and:

Firestore pubs/{eventId}
        │
        ├── occurrence due within 7 days
        │
        ▼
event_due Listener
        │
        ▼
      Fact
        │
        ▼
 Event Poll Creation Cell
        │
        ├── poll already exists?
        │       │
        │       └── yes → complete successfully
        │
        └── no
             │
             ├── create poll
             ├── create votes document
             ├── create attendance document
             └── create audit record
4. Event Venue Data Model

Recurring events are represented by documents in:

pubs/{eventId}

A venue participates in this service only when:

venueType == "event"

The venue contains a recurrence definition and a persisted occurrence date.

The persisted date represents:

The next calculated occurrence of this event.

It does not represent the original start date of the recurrence.

5. Recurrence Data Model

The recurrence definition supports:

frequency:
    once
    weekly
    monthly
    yearly

Additional recurrence fields are determined by the frequency.

Supported concepts include:

date
interval
weekdays
weekday
nth
month
month_day

Weekdays use:

Monday = 0
Tuesday = 1
Wednesday = 2
Thursday = 3
Friday = 4
Saturday = 5
Sunday = 6

The recurrence schema must not contain a separate start_date field.

The persisted event date itself provides the recurrence state.

Note that the recurrence rule's own `date` field is distinct from the venue's
persisted occurrence field described in section 6. The rule's `date` is the
configured occurrence of a `once` recurrence; the venue's field is mutable
calculated state.

6. Persisted Event Date

The venue contains:

next_occurrence_date: YYYY-MM-DD

This field name is a frontend/backend compatibility contract and must not be
changed independently by either side.

This field represents the next occurrence that has been calculated for the event.

There are two valid initial conditions.

6.1 New recurrence

If the event has no persisted date:

next_occurrence_date does not exist

the recurrence calculation uses the current date/time as its reference point.

The implementation must derive the effective current date from the service's normal clock.

There is no separate recurrence start date.

6.2 Existing recurrence

If the event has a persisted date, that date represents the previously calculated next occurrence.

The recurrence calculation can therefore use the stored date as the recurrence state from which the next occurrence is derived.

The reference date supplied to the calculator must be strictly later than the
stored occurrence, otherwise the calculator returns the stored occurrence again
and the venue never advances.

A venue that has been dormant for a long period must not have to advance one
occurrence per Cell execution to catch up. The reference is therefore:

max(storedDate + 1 day, today)

A consequence of removing start_date is that, for interval > 1, this re-anchors
the cadence on the reference date rather than preserving the original phase.
This is accepted.

7. Recurrence Calculation

The recurrence calculator must be deterministic.

Given the same recurrence definition and reference state, it must produce the same next occurrence.

Supported recurrence forms are:

7.1 Once

The configured date represents the occurrence.

If the occurrence has already passed, no future occurrence exists.

7.2 Weekly

Weekly recurrence supports:

one or more weekdays;
an interval measured in weeks.

The next valid occurrence is calculated according to the configured weekday(s) and weekly interval.

7.3 Monthly

Monthly recurrence supports either:

a specific day of the month; or
an nth weekday of the month.

An interval measured in months may be specified.

Invalid dates must not silently produce a different date.

7.4 Yearly

Yearly recurrence supports either:

a specific month/day; or
an nth weekday of a specified month.

An interval measured in years may be specified.

Invalid dates must not silently produce a different date.

8. stale_events Listener

The first listener is named:

stale_events

Its purpose is to identify event venues whose persisted occurrence date needs to be calculated or advanced.

The listener watches:

pubs

and is interested in event venues where:

venueType == "event"

and:

next_occurrence_date does not exist

or:

next_occurrence_date is in the past

or:

next_occurrence_date is no longer what the current recurrence definition would
produce for today

The third condition exists because the recurrence definition itself can be
edited (for example, from the frontend) without next_occurrence_date changing.
A stored date that is still in the future is not evidence that it remains
correct; it is only evidence relative to whichever recurrence definition
produced it. The listener must therefore treat a mismatch between the current
recurrence definition and the stored date as stale, exactly as it treats a
past or missing date.

The listener creates a Fact representing the required recurrence calculation.

The listener does not itself calculate or update the date.

8.1 Date Boundary Re-evaluation

Eligibility depends on today, but a Firestore subscription only delivers changes
to documents. A venue can therefore become eligible purely because the calendar
date advanced, with no document having changed.

Both listeners must therefore re-evaluate their eligibility predicate
periodically as well as on document change. The interval is configuration,
defaulting to 24 hours.

Re-evaluation re-reads the current event venues from Firestore. It must not
maintain its own in-memory copy of the collection; the venue cache is a separate
concern that will serve this purpose later.

Re-evaluation creates Facts unconditionally for every eligible venue. Suppressing
repeated work is the idempotency component's responsibility and must not be
duplicated in the listener.

9. stale_events Idempotency

The idempotency key for the listener/fact is:

{eventId}_{next_occurrence_date}_{recurrenceHash}

where:

eventId is the Firestore document ID;
next_occurrence_date is the currently observed persisted occurrence;
recurrenceHash is a deterministic content hash of the current recurrence definition.

When no occurrence is persisted, the literal:

none

is used in its place of next_occurrence_date.

The recurrence hash is required, not cosmetic. Without it, editing the
recurrence definition without changing next_occurrence_date would compute the
same key as before, which is already PRESENT in the idempotency store; the
resulting Fact would be silently suppressed and the edit would never be picked
up. Including the hash means an edited recurrence definition produces a new key
regardless of whether next_occurrence_date has changed yet, so the Cell is
allowed to run and recompute.

The hash must be computed over a canonical representation of the recurrence
map so that semantically identical definitions always hash identically
regardless of field ordering.

A consequence is that the missing-date key resolves once per distinct
recurrence definition and is thereafter suppressed for that definition. A
venue that returns to having no occurrence under an unchanged recurrence
definition will not produce a further Fact. This is accepted.

The idempotency key belongs to the stale_events idempotency namespace.

A separate listener may therefore legitimately use the same textual key.

Idempotency namespaces are independent.

10. Stale Event Cell

The Fact creates a Stale Event Cell.

The Cell receives the event identity and the relevant observed date/state.

The Cell then:

Reads the current venue document.
Verifies that it is still an event venue.
Reads the current recurrence definition.
Determines the current persisted occurrence date.
Calculates the next required occurrence.
Updates the venue's next_occurrence_date field.

The Cell must operate against current Firestore state rather than blindly trusting the values that caused the original listener event.

11. Replay Behaviour of Stale Event Processing

Stale event processing must be safe to replay.

Consider:

next_occurrence_date = 2026-08-20

A stale-event Cell calculates and writes:

next_occurrence_date = 2026-09-20

If the original event is subsequently replayed, the second execution observes:

next_occurrence_date = 2026-09-20

and therefore no longer considers the event stale.

The second execution must not incorrectly advance the event again.

This is an important property of the design.

The first successful state transition changes the conditions under which the work is eligible.

12. Event Due Listener

The second listener is responsible for poll materialisation.

It watches:

pubs

for event venues whose next occurrence is within the poll creation window.

The creation window is:

occurrence date - 7 days

through:

occurrence date

inclusive.

An event is therefore eligible for poll creation when:

today <= next_occurrence_date <= today + 7 days

An occurrence in the past is not due; it is stale. The two predicates are
therefore mutually exclusive, and a venue produces at most one Fact per
evaluation.

The listener creates a Fact for the event occurrence.

The listener does not create the poll itself.

13. event_due Idempotency

The idempotency key for the event-due listener/fact is:

{eventId}_{next_occurrence_date}

This is intentionally the same textual key format used by stale_events.

The two listeners have separate idempotency namespaces.

Therefore:

stale_events:
    namespace = stale_events
    key       = {eventId}_{next_occurrence_date}

event_due:
    namespace = event_due
    key       = {eventId}_{next_occurrence_date}

These are independent idempotency identities.

This is desirable because the two listeners represent different operations:

one calculates recurrence state;
the other materialises a poll.
14. Event Poll Creation Cell

The event-due Fact creates an Event Poll Creation Cell.

The Cell receives:

eventId
occurrenceDate

The Cell operates against current Firestore state.

Before creating anything, it must establish whether the required poll already exists.

15. Poll Identity

Poll documents must use normal Firestore-generated document IDs.

The old deterministic format:

event-{eventId}-{YYYY-MM-DD}

is not part of the new architecture.

A newly-created poll therefore looks like:

polls/{firestoreGeneratedDocumentId}

The poll contains sufficient business data to identify the event occurrence, including:

eventVenueId
date

and the normal poll fields.

16. Poll Existence Check

The Event Poll Creation Cell must perform a business-level idempotency check before creating a poll.

It searches the polls collection for a poll matching:

eventVenueId == eventId
date == occurrenceDate

If such a poll already exists:

poll already exists

the Cell treats the desired state as already achieved.

It must:

create no new poll;
create no duplicate votes document;
create no duplicate attendance document;
not treat the situation as an error;
complete successfully.

This is an explicit correctness rule, not merely an optimisation.

17. Poll Creation

If no matching poll exists, the Cell creates a new poll using a Firestore-generated document ID.

The poll contains at least:

date: occurrenceDate
completed: false
pubs:
    eventId: ...
eventVenueId: eventId
eventOccurrenceDate: occurrenceDate

The exact normal poll schema is defined elsewhere.

The important invariant for this service is that the poll identifies the event and occurrence date.

18. Associated Documents

When a new event poll is created, the Cell also creates the associated documents required by the normal poll model.

At minimum:

votes/{pollId}
attendance/{pollId}

with their normal initial contents.

These documents are part of poll materialisation.

19. Poll Creation Audit

A successful new poll creation produces an immutable audit record.

The audit records that the backend automatically created the poll.

The audit must identify at least:

pollId
actionType = create
actorUid = backend:auto
pollDate
timestamp

The precise audit storage mechanism follows the application's normal audit conventions.

Audit data is historical evidence and must not be used as the source of truth for whether the poll exists.

20. Creation Idempotency and Race Protection

There are deliberately two layers of protection against duplicate poll creation.

Layer 1 — Cell idempotency

The listener/fact uses:

{eventId}_{date}

within the event_due namespace.

This prevents normal repeated listener observations from producing duplicate Cells.

Layer 2 — Business-state existence check

The Cell searches Firestore for an existing poll matching:

eventVenueId == eventId
date == occurrenceDate

This protects against situations where duplicate work reaches the Cell despite listener/fact idempotency.

The Cell must never assume that execution idempotency guarantees database uniqueness.

21. Concurrency Consideration

The business existence check is required because the system does not rely upon exactly-once execution.

Two Cells could theoretically reach the creation step independently.

Therefore, the implementation must consider the race:

Cell A                    Cell B
  │                         │
  ├─ search: no poll        ├─ search: no poll
  │                         │
  ├─ create poll            ├─ create poll
  │                         │
  ▼                         ▼
       duplicate polls

A simple read-then-create operation is therefore not, by itself, a mathematically complete uniqueness guarantee.

The implementation must use the application's available Firestore mechanisms to determine whether stronger atomic protection is required.

If the application can perform an atomic uniqueness claim or transaction, that should be preferred.

If the architecture deliberately accepts the query-then-create model, this limitation must be explicitly accepted as an implementation trade-off.

The CDD therefore requires the existence check, but does not pretend that an ordinary non-transactional query is an atomic uniqueness constraint.

22. Interaction Between the Two Listeners

The two listeners deliberately operate on the same venue state but perform different work.

For example:

event:
    next_occurrence_date = 2026-08-20

The event is within seven days of its occurrence.

The event_due listener can therefore create poll materialisation work.

After the occurrence becomes stale, the stale_events listener calculates the next occurrence.

The resulting state may become:

next_occurrence_date = 2026-09-20

The old occurrence is no longer eligible for event-due processing.

This means replay of stale-event processing does not continually advance the recurrence.

The persisted date is the state that determines eligibility.

23. Safety Properties

The implementation must preserve the following invariants.

Invariant 1 — Event venues only

Only documents with:

venueType == "event"

participate in recurrence processing.

Invariant 2 — Persisted date means next occurrence

The venue's next_occurrence_date represents the next calculated occurrence.

It is not an immutable recurrence start date.

Invariant 3 — Missing date is valid initial state

A new recurring event may have no next_occurrence_date.

The first stale-event calculation uses the current date as its reference.

Invariant 4 — Stale processing converges

Once a stale event Cell successfully advances the date, replay of the same work must observe the new state and not advance it repeatedly.

Invariant 5 — Polls use normal Firestore IDs

Poll document IDs are generated by Firestore.

The event ID and occurrence date are business data, not an encoded Firestore document identity.

Invariant 6 — Existing polls are not recreated

If a poll already exists for:

(eventVenueId, occurrenceDate)

poll creation is considered already complete.

Invariant 7 — Poll creation is retry-safe

Repeating the Event Poll Creation Cell must converge on one existing poll rather than deliberately creating another.

Invariant 8 — Cell execution state is not business state

Transient execution state belongs to Cellar.

The Firestore venue and poll documents represent durable application state.

24. Failure and Retry Semantics

The service must not depend on exactly-once execution.

Cells may be retried after:

process failure;
network failure;
Firestore failure;
ambiguous completion of an external/database operation.

The implementation should prefer convergence through re-reading current state.

For recurrence:

read current next_occurrence_date
    ↓
calculate required next occurrence
    ↓
write next_occurrence_date

For poll creation:

read current event state
    ↓
check whether poll exists
    ↓
create only if required

A retry must therefore determine whether the desired state has already been achieved before performing the operation again.

25. Date and Time Semantics

Event recurrence operates on calendar dates rather than arbitrary timestamps.

The service's effective timezone is:

Europe/London

The current local calendar date must therefore be determined using Europe/London semantics.

Recurrence calculations must not depend on the server's incidental local timezone.

26. Configuration and Defaults

The poll creation lead time is:

7 days

The recurrence calculation must use the supported recurrence schema and normal application defaults.

Any configurable values should be specified separately from the core recurrence algorithm.

28. Required Cells

The new implementation requires at least the following Cells.

28.1 Stale Event Cell

Purpose:

Calculate and persist the next occurrence date for an event.

Inputs:

eventId
observedDate/state

Responsibilities:

read current event document;
verify event venue;
read recurrence;
determine current persisted date;
calculate next occurrence;
update the venue next_occurrence_date when required;
safely converge when replayed.
28.2 Event Poll Creation Cell

Purpose:

Materialise the poll for a due event occurrence.

Inputs:

eventId
occurrenceDate

Responsibilities:

read current event state;
verify the occurrence is still the intended occurrence;
search for an existing poll for (eventVenueId, occurrenceDate);
treat an existing poll as successful completion;
otherwise create a Firestore-ID poll;
create associated votes and attendance documents;
create the poll creation audit record;
safely converge on retry.
29. Required Listeners
29.1 stale_events

Watches:

pubs

Eligibility:

venueType == "event"
AND
(
    next_occurrence_date does not exist
    OR
    next_occurrence_date < today
    OR
    next_occurrence_date does not match what the current recurrence definition
    would produce for today
)

Produces a Fact and ultimately a Stale Event Cell.

Idempotency namespace:

stale_events

Idempotency key:

{eventId}_{next_occurrence_date}_{recurrenceHash}
29.2 event_due

Watches:

pubs

Eligibility:

venueType == "event"
AND
next_occurrence_date is within the next 7 days

Produces a Fact and ultimately an Event Poll Creation Cell.

Idempotency namespace:

event_due

Idempotency key:

{eventId}_{date}
30. Implementation Notes

The listener should be responsible only for identifying state that requires work.

The Fact identifies the work.

The Cell performs the work.

The Cell must always re-read current Firestore state before making consequential decisions.

The architecture should avoid embedding business operations directly into listener callbacks.

In particular:

recurrence calculation belongs in the Stale Event Cell;
poll existence checks belong in the Event Poll Creation Cell;
poll creation belongs in the Event Poll Creation Cell;
associated document creation belongs in the Event Poll Creation Cell.
31. Conformance Requirements

A conforming implementation must:

Use listener-driven processing rather than scheduled housekeeping for recurrence maintenance.
Monitor pubs for stale or missing event dates.
Create a Fact for stale event processing.
Execute recurrence calculation in a Cell.
Persist the calculated next occurrence in the event's next_occurrence_date field.
Not use a separate start_date field for recurrence state.
Use the current date as the reference for a new event with no persisted date.
Ensure stale-event replay converges after the date has been advanced.
Monitor event venues whose occurrence is within the seven-day poll creation window.
Create a Fact and Cell for poll materialisation.
Use {eventId}_{next_occurrence_date} as the event-due idempotency key.
Keep stale-event and event-due idempotency namespaces separate.
Use Firestore-generated document IDs for polls.
Store the event identity and occurrence date as poll business data.
Check for an existing poll matching (eventVenueId, occurrenceDate) before creating one.
Treat an existing matching poll as successful completion.
Create votes and attendance documents when a new poll is materialised.
Record poll creation in the audit trail.
Make Cell execution safely retryable.
Avoid relying on exactly-once execution for correctness.
Use Europe/London calendar-date semantics for determining "today".
Preserve the invariant that one event occurrence should result in one logical poll.
32. Fundamental Design Principle

The service must not attempt to guarantee correctness by assuming that listeners or Cells execute exactly once.

Instead:

Listener idempotency
        +
Cell replay safety
        +
current database state
        +
business-level existence checks
        =
convergent behaviour

The important distinction is:

Idempotency prevents repeated work from normally being initiated; database state determines whether the desired outcome already exists.

For event poll creation, the Cell therefore must not regard its idempotency key as sufficient protection against duplicate polls.

The authoritative business question is:

Does a poll already exist for this event occurrence?

If the answer is yes, the Cell has nothing further to do.
