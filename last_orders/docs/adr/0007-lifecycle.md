# ADR: Application Lifecycle and Graceful Shutdown

## Status

Accepted

## Context

Last Orders is primarily a long-running application composed of several different kinds of components.

Some components continuously produce work:

* database listeners;
* HTTP endpoints and webhook listeners;
* active caches or subscriptions.

Other components execute work when requested:

* Cellar Cells;
* Cell Sequences;
* service operations such as sending email or updating recurrence.

Cellar provides the application's execution model, including:

* Fanout;
* Cell Sequences;
* retry behaviour;
* delayed execution through `NotBefore`.

Consequently, the application does not require a separate general-purpose lifecycle mechanism for service execution. Lifecycle management is principally concerned with the application's long-running infrastructure and with coordinating orderly startup and shutdown.

The primary graceful shutdown requests available to the application are:

* `SIGINT`, normally generated by Ctrl-C;
* `SIGTERM`, normally generated by a process supervisor, container runtime, or orchestrator.

Many other forms of process termination do not permit graceful handling:

* power loss;
* `SIGKILL`;
* out-of-memory termination;
* process or system crashes.

The application must therefore be designed so that graceful shutdown is useful when available, but correctness must not depend upon receiving a graceful shutdown notification.

## Decision

### Root shutdown context

The application will have a root shutdown context representing the request for the application to terminate gracefully.

The first `SIGINT` or `SIGTERM` will cancel this context and initiate graceful shutdown.

Conceptually:

```text
SIGINT or SIGTERM
        ↓
Cancel root shutdown context
        ↓
Begin graceful shutdown
```

The root shutdown context represents:

> The application is shutting down and should stop accepting or producing new work.

It does not necessarily mean that all in-flight work must immediately be cancelled.

### Graceful shutdown ordering

Shutdown will generally occur in the reverse direction of work flow.

The application will:

1. stop components that produce or accept new work;
2. allow already accepted work to complete where appropriate;
3. stop execution infrastructure;
4. close underlying resources.

For example:

```text
Normal operation:

Listener / Endpoint
        ↓
      Truth
        ↓
      Fanout
        ↓
    Cellar Cell
        ↓
External Service


Shutdown:

1. Stop Listener / Endpoint
2. Stop accepting new work
3. Drain in-flight Cellar work
4. Stop execution infrastructure
5. Close external resources
```

This prevents new work from being introduced into infrastructure that has already been stopped.

### Startup ordering

Startup will follow the direction of work flow in reverse.

The application will generally:

1. construct all components;
2. initialise execution infrastructure;
3. initialise required state infrastructure, such as caches;
4. start components which produce or accept work.

This ensures that producers cannot introduce work before the infrastructure required to process it is ready.

### In-flight work

Graceful shutdown distinguishes between:

* **new work**, which should no longer be accepted once shutdown begins;
* **in-flight work**, which may be allowed to complete.

The application will provide a bounded grace period for in-flight work to finish.

After that grace period expires, remaining work may be cancelled as required by the hosting environment.

This is particularly important when running under systems which impose their own termination deadlines, such as container or orchestration platforms.

### Escalating Ctrl-C behaviour

The first shutdown signal requests graceful shutdown.

Subsequent Ctrl-C signals may be used to request an immediate abort if graceful shutdown is taking too long.

The exact escalation threshold is an application UX decision. The intended behaviour is:

```text
First Ctrl-C:
    Begin graceful shutdown

Further Ctrl-C:
    Escalate towards immediate process termination
```

This provides an operator with a means of abandoning graceful shutdown when necessary.

`SIGTERM` is treated as a request for the same graceful shutdown behaviour as the first Ctrl-C.

### No general lifecycle framework

The application will not initially introduce a generic lifecycle abstraction such as:

```go
type Lifecycle interface {
    Start(context.Context) error
    Stop(context.Context) error
}
```

or require all components to implement a common lifecycle interface.

Instead, lifecycle orchestration will initially be explicit in the application composition layer.

Conceptually:

```go
func Run(ctx context.Context) error {
    // Construct components.

    // Start execution infrastructure.

    // Initialise required state.

    // Start producers.

    // Wait for shutdown request.

    // Stop producers.

    // Drain in-flight work.

    // Stop execution infrastructure.

    // Close resources.
}
```

A more general lifecycle abstraction may be introduced later if repeated, well-understood lifecycle patterns emerge.

### Correctness must not depend on graceful shutdown

The application must tolerate ungraceful termination.

A process may disappear without receiving any shutdown notification.

Therefore:

* work must tolerate retry;
* externally visible operations should be idempotent where required;
* persisted state must not rely solely on shutdown-time flushing;
* observing an event more than once should be preferable to silently losing it.

Graceful shutdown is an optimisation for orderly operation, not a guarantee of correctness.

## Consequences

### Positive

* Startup and shutdown behaviour is explicit and easy to inspect.
* Producers are stopped before consumers, reducing the risk of introducing work into stopped infrastructure.
* Cellar remains responsible for execution semantics rather than lifecycle code duplicating its responsibilities.
* In-flight work can be given an opportunity to complete.
* The application remains correct when graceful shutdown is unavailable.
* Operators can escalate a stuck graceful shutdown to an immediate abort.

### Negative

* Lifecycle ordering is initially expressed explicitly in application code rather than hidden behind a generic abstraction.
* The application composition layer must understand the dependency ordering of its long-running infrastructure.
* Some components may require explicit shutdown or draining APIs.
* Graceful shutdown requires careful definition of which work may continue and for how long.

## Result

Lifecycle management is primarily concerned with the application's long-running producers and infrastructure.

Cellar Cells and Cell Sequences represent units of work and use Cellar's execution, retry, and Fanout mechanisms. They are not themselves treated as permanently running application services.

The application's root shutdown context represents a request to begin graceful termination, normally caused by `SIGINT` or `SIGTERM`.

Graceful shutdown proceeds by stopping the production of new work, draining work already in progress where appropriate, and only then closing execution infrastructure and external resources.
